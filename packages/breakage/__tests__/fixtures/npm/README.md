# npm fixture projects

Each directory is a miniature consumer project: its package source, manifests, Breakage configuration, contracts, and frozen peer environments live together. Local packages keep their own `package.json` beside `src/`. Alternate source files represent deliberate case-specific changes to the same package.

| Project                 | Behavior                                                                                                                                                        |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `candidate-minimatch`   | A host written for Minimatch 8, with complete Minimatch 8 and 9 environments. The default configuration selects 8; the incompatible case selects 9.             |
| `candidate-peer-ranges` | A coordinated host and integration sharing renderer 18. Cases vary declarations, optionality, prerelease versions, or the integration's direct renderer import. |
| `runtime-dependencies`  | A shared host reached through an optional helper package. Cases make the helper required, remove its manifest, or introduce a shadow peer.                      |
| `coupled-peers`         | A representative containing host 1 and renderer 19, with a contract for each relationship.                                                                      |

The [shared project](../../../tests/public/fixtures/npm) supplies the public consumer contracts, released host environments, and a candidate environment template. It lives inside the public restore boundary so released contracts retain all their inputs. Tests can select new labels and versions by cloning these authored environments.

The [fixture harness](../../../tests/public/npm-fixture.ts) copies a whole project, applies a case's changes, compiles each `src/index.ts` to its manifest's `main`, and packs the local packages offline. It preserves bare peer imports. Runtime workspace dependencies become absolute tarball paths only in the disposable copy. Frozen lock files remain authored fixture inputs. Installed `node_modules` trees and authoring `dist` outputs are excluded from copies so every test rebuilds its own source and establishes its own dependency installation.

The Minimatch environments own their exact published dependency pins and registry lock files. Repository installation runs `pnpm run test:fixtures:prepare` to install these environments and populate the fixture's ignored `.cache/` directory. Disposable copies include that cache and install their frozen dependencies offline; no outer aliases or repacked registry packages supply their dependencies. Rerun preparation after changing an environment or installing with scripts disabled. Frozen representatives remain outside the pnpm workspace; their npm lock files are their only installation authority. These fixed regression environments remain under Renovate's default fixture exclusion.

Current fixture packages are private workspace members with unique package names, exports, and `workspace:*` development dependencies. The shared [Vite Plus configuration](../../../../../scripts/fixture-tasks.ts) orders upstream builds before fixture builds and project type checks. Each project's TypeScript configuration checks sources, configuration, and contracts through actual package declarations, without source aliases or manual dependency links. Optional runtime dependencies that are also needed to compile a fixture are declared as development dependencies so they participate in the build graph. Historical package sources remain outside the workspace and are checked with their containing project.

Run `pnpm run check:tsc` from the repository root to build prerequisites and check every project. `pnpm run build` also builds all current fixture packages. The Minimatch authoring packages resolve their declared supported peer range through the development workspace; the exact Minimatch 8 and 9 runtime installations still come exclusively from their frozen representatives. Run compatibility tests through the repository test commands so every candidate is rebuilt and executed inside its disposable repository.
